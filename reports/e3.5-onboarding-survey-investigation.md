## 1. The chat-surface runner, reproduced in full

`apps/web/src/lib/onboarding/service.ts` (329 lines), `handleOnboarding(socio, incomingMessage, channel)`:

- **Sequencing state machine**: driven by `socio.status` — `NEW` → `AWAITING_LANGUAGE` →
  (optionally `AWAITING_CONSENT`, currently disabled via `REQUIRE_LEGAL_CONSENT = false`, line 18) →
  `AWAITING_NAME` (despite the name, this is the **generic** step handler for every step, not just a
  name field — confirmed at lines 148-215) → `ACTIVE`.
- **Which step is current**: `socio.promptOverrides.onboardingStep`, a plain number, read at line 152
  and written at line 193/264. This is JSON stored directly on the `Socio` row (`promptOverrides`),
  not a dedicated column.
- **Per-step validation**: `stepField === "name"` gets name-extraction (`extractName`, an AI call) with a
  localized retry message on failure (lines 166-172); every other field just checks
  `value.length >= 2` when `required` (lines 174-179). On failure, the same question is re-sent
  (`getStepRetryMessage`) and `promptOverrides.onboardingStep` is **not** advanced — the learner is stuck
  on the same step until they answer.
- **Answer storage — the important finding**: `updateData[stepField] = value; await
  repo.updateSocio(socio.id, updateData)` (lines 183-186, 194). **Each step's answer is written to a
  column on the `Socio` model itself, named by the step's own `field` string.** This only works because
  `Socio` happens to have matching columns for the fields this mechanism was built for (`name`,
  `businessDescription` — the latter has its own hardcoded legacy case at lines 219-234,
  `AWAITING_BUSINESS`, explicitly marked deprecated). **This does not generalize.** AI Essentials' 7
  survey questions (major/year, target job, AI-usage frequency, a tedious task, beliefs about AI,
  self-rated confidence) have no corresponding `Socio` columns — reusing this exact storage mechanism
  for a new course would mean adding 5+ new bespoke columns to `Socio`, which is the wrong shape for a
  per-course, author-defined question list. **The chat-surface runner's sequencing state machine is a
  good pattern to mirror; its storage mechanism is not.**
- **Completion**: transitions to `ACTIVE`, calls `repo.initProgress`, sends a welcome message via
  `sendWelcome` → `buildWelcomeForSocio` → `buildWelcomeMessage` (`courses/course-meta.ts:293-311`).
  **No existing closing-message mechanism reads back a specific captured answer** — the welcome message
  interpolates `{mentorName}`/`{courseName}`/`{participantName}` only (see §5).

## 2. Player-surface equivalent — design

**Confirmed: the "renders in-thread, completes on chat-input response" mechanics are the right base to
extend, but multi-question sequencing needs one small addition beyond what `project`/`teach +
expectsResponse` have today — a step-index counter, not a new completion model.**

- `project` (E.3, `journey-package.schema.ts`'s `project` union member) and `teach + expectsResponse`
  both complete in **one round trip**: render content, learner types once, `complete()` fires, block is
  done. Confirmed by re-reading `gradePlayerBlock`'s `teach` branch (`service.ts:609`, unconditional
  `complete: true` on any single call) and E.3's fallthrough (same shape). Neither has a notion of "not
  done yet, ask the next thing."
- `teach_back`'s `turnCount` state is the existing precedent for exactly this need: a small integer
  counter persisted in `BlockProgress.state` (JSON), read back on each subsequent call
  (`service.ts:303-304`: `const state = existing?.state as {turnCount?: unknown} ...; const turnCount =
  typeof state.turnCount === "number" ? state.turnCount : 0;`), compared against a threshold to decide
  "advance the internal step" vs. "complete the block" (`service.ts:307`, `517`).
- **Design**: a new block type or a `project`-adjacent extension (open question, see below) that stores
  `BlockProgress.state = { stepIndex: number, answers: Record<string, string> }`. Each learner submission
  through the shared textarea (same `complete()`/`/complete` route every block already uses — no new
  route needed, confirmed against E.1's finding that this route is already generic) is graded like this:
  record the answer under the current step's `id` in `state.answers`, increment `stepIndex`, and return
  `complete: stepIndex >= steps.length` — i.e. the block only reports done to the client once every
  question has been answered, exactly mirroring `teach_back`'s `turnCount >= threshold` shape but with a
  per-course-configurable step count instead of a hardcoded 2.
- **One real design fork, not resolved here**: should this be a *new* `blockType` (e.g. `"onboarding_survey"`)
  in `lessonBlockSchema`, or should `config.onboarding.mode: "survey"` stay a package-level, non-block
  construct with its own dedicated gate (mirroring how `baseline_quiz`/diagnostic is *not* a block in
  `blocks[]` today — it's a pre-lesson full-page gate, confirmed at `service.ts:469-477`)? The chat-surface
  precedent and the AI Essentials doc both treat onboarding as something that runs once, before Lesson 1,
  not as a block inside a lesson's `blocks[]` array — this argues for following the diagnostic's existing
  shape (a `getLessonDto`-level gate, not a lesson block) rather than inventing a competing in-thread block
  type. Flagging as the one thing worth Michael's explicit call before implementation, since it changes
  where the render logic lives (a dedicated pre-lesson screen/route vs. `LessonPlayer.tsx`'s block switch).

## 3. Storage location — durable and (eventually) readable

- **`BlockProgress.state`/`.response`** (JSON, already player-surface-writable, no new plumbing) is
  sufficient and safe for E.3.5's own scope: `state.stepIndex` for in-progress sequencing (mirroring
  `teach_back`), `response` (or `state.answers`) for the final full answer set once the survey completes —
  same "no new table" principle E.3 already established for `project`. If onboarding is built as a
  pre-lesson gate rather than a `blocks[]` entry (per §2's fork), it still needs *some* `BlockProgress`-like
  row to key off — either a synthetic `blockId` (e.g. `"__onboarding_survey__"`) the same way the diagnostic
  uses `DiagnosticAttempt` as a dedicated table rather than `BlockProgress`, or a new dedicated table
  mirroring `DiagnosticAttempt`'s shape. Worth deciding alongside the §2 fork, not independently.
- **`SocioContext` is confirmed NOT reachable from the player surface today.** Grepped
  `apps/web/src/lib/player` and `apps/web/src/lib/messaging` for `contextExtractor`/`upsertSocioContext` —
  the only import of `extractAndStoreContext` is in `messaging/handler.ts:10` (chat-surface only,
  fire-and-forget after an AI response). Writing onboarding answers into `SocioContext` from the player
  surface would be new plumbing, not a reuse of existing machinery.
- **Recommendation**: store in `BlockProgress`/a dedicated table (per §2's fork) for now — this is what
  E.3.5 needs to ship a working survey. **Do not** try to also wire this into `SocioContext` or the prompt
  layer in the same stage — that's the separately-scoped, already-flagged 1.11 gap (Track E's session has
  this on record as non-blocking, deferred). Whatever table E.3.5 picks should just not be something a
  later "surface this in the prompt" fix would need to migrate away from — a plain JSON blob keyed by
  step `id` (not by hardcoded field names, unlike the chat-surface mechanism) satisfies that: any future
  reader can iterate `Object.entries(answers)` generically.

## 4. Survey + diagnostic sequencing

Confirmed today's exact coupling: `diagnosticRequired = access.config.onboarding?.mode ===
"baseline_quiz"` (`service.ts:473`) — the diagnostic gate is keyed on `mode` being **exactly**
`"baseline_quiz"`, not on `diagnostic`'s presence. Nothing in the schema actually prevents a package from
setting `mode: "survey"` *and* populating `diagnostic` at the same time — `mode` and `diagnostic` are
independent optional fields on the same `configSchema.onboarding` object
(`journey-package.schema.ts:714-722` in the current file, `mode`/`steps`/`diagnostic` all siblings). The
runtime just never learned to look at `diagnostic` unless `mode` said so.

**Three options, with tradeoffs:**

- **(a) New enum value `"survey_then_diagnostic"`.** Requires a schema change (one new enum member) *and*
  bespoke runtime logic that only that one value triggers ("run steps, then run diagnostic"). Couples
  survey+diagnostic sequencing to a single named combination — a future course wanting diagnostic-then-survey,
  or three onboarding stages, needs another bespoke enum value each time. Weakest generalization, smallest
  one-off diff.
- **(b) Decouple the diagnostic gate from `mode` entirely — recommended.** Change `diagnosticRequired`'s
  condition from `mode === "baseline_quiz"` to `!!access.config.onboarding?.diagnostic` (presence-based,
  not enum-based), and add a parallel survey-required gate keyed on `mode === "survey" && steps.length > 0
  && <survey not yet complete>`, checked *before* the diagnostic gate in `getLessonDto` (mirroring the
  existing `learnerProjectSelectionRequired` → `diagnosticRequired` → lesson-body sequential-gate shape
  already at `service.ts:469-478`). AI Essentials then authors `mode: "survey"` with `steps` **and** a
  populated `diagnostic` — no new enum value, and any future course gets survey+diagnostic (or diagnostic
  alone, or survey alone) for free from the same two orthogonal checks. This is the smaller change in
  spirit even though it touches one more existing line (`diagnosticRequired`'s condition) — it removes a
  false coupling rather than adding a new named case for one combination.
- **(c) A `stages: Array<"survey" | "baseline_quiz">` ordering list.** More general (arbitrary ordering,
  arbitrary repetition), but solves a problem nobody has yet — no course today needs anything beyond
  "survey then diagnostic," and this adds real schema surface for a generalization with zero current
  demand. Not recommended for this stage; (b) can grow into this later if a real need appears.

**Leaning toward (b)** — it's consistent with `mode`/`diagnostic` already being independent schema fields
today (the runtime is the thing that's inconsistently coupled, not the schema), and it costs one changed
condition plus one new parallel gate, not a new enum value.

## 5. Closing message — reuse `buildWelcomeMessage`'s interpolation pattern

`buildWelcomeMessage` (`apps/web/src/lib/courses/course-meta.ts:293-311`) already does exactly the kind of
substitution the doc wants, just with fixed platform-known values: a `localizedStringSchema` template
resolved via `resolveLocalized`, then `.replace(/{placeholder}/g, value)` for `{mentorName}`,
`{courseName}`, `{participantName}` (lines 303-308).

**Proposed mechanism, smallest addition**: a new optional field on `config.onboarding` (or wherever E.3.5's
survey config lives per §2's fork) — e.g. `closingMessage: localizedStringSchema.optional()` — authored
with a `{q5}`-style placeholder (or, more generally, `{step:<id>}` so it isn't hardcoded to a specific
question index — AI Essentials only needs Q5, but a generic `{step:<id>}` costs nothing extra and doesn't
lock the mechanism to this one course). At completion time, resolve the template the same way
`buildWelcomeMessage` does, substituting each `{step:<id>}` token with `state.answers[id]` before sending.
This is a static authored string with dynamic substitution — not a full AI-generated closing message —
matching the doc's own instruction ("restate their answer... and say plainly") and the existing precedent
exactly, no new interpolation mechanism invented.

## Recommended design (for Michael's approval, not a decision)

1. **Sequencing**: a `stepIndex` counter in a `BlockProgress`-shaped JSON state, mirroring `teach_back`'s
   `turnCount` pattern exactly (§2).
2. **Placement**: lean toward a pre-lesson gate (like the diagnostic), not a `blocks[]` entry — but this is
   the one open fork flagged in §2 and should get an explicit answer before implementation, since it
   determines whether new render code lives in `LessonPlayer.tsx`'s block switch or in a dedicated
   pre-lesson screen/route alongside the diagnostic's.
3. **Storage**: JSON keyed by step `id` (not named columns, unlike the chat-surface mechanism) — either
   `BlockProgress` if built as a block, or a small dedicated table mirroring `DiagnosticAttempt`'s shape if
   built as a pre-lesson gate. Explicitly not wired into `SocioContext` or the prompt layer in this stage —
   that stays the separately-tracked 1.11 gap.
4. **Sequencing with the diagnostic**: option (b) from §4 — decouple `diagnosticRequired` from `mode`,
   gate on `diagnostic`'s presence directly, add a parallel survey-required gate checked first.
5. **Closing message**: a new optional `closingMessage: localizedStringSchema` with `{step:<id>}`
   placeholder substitution, reusing `buildWelcomeMessage`'s exact `.replace(/{...}/g, ...)` pattern.

Do not begin implementation — awaiting approval.
